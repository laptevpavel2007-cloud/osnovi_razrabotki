# Спецификация проекта Tech Shop

## 1. Назначение системы

**Tech Shop** — это desktop-приложение для автоматизации работы магазина электроники. Система предназначена для продавцов-консультантов и кассиров, позволяя им:
- Вести каталог товаров с контролем остатков на складе
- Оформлять продажи с формированием электронных чеков
- Принимать товары на склад (приёмка)
- Обрабатывать возвраты товаров от покупателей
- Собирать ПК на заказ из комплектующих
- Анализировать статистику продаж

Система заменяет бумажный учёт, обеспечивает контроль целостности данных (остатки не могут уйти в минус) и предоставляет инструменты для сложных операций (частичные возвраты, конфигуратор ПК).

## 2. Функциональные требования

### 2.1. Управление каталогом и складом

| ID | Требование | Приоритет |
|----|-----------|-----------|
| **FR-01** | Система должна отображать каталог всех товаров с указанием названия, цены и текущего остатка на складе. | Высокий |
| **FR-02** | Каталог должен быть сгруппирован по категориям: Бытовая техника, Комплектующие для ПК, Ноутбуки и планшеты, Аксессуары, Периферия. | Высокий |
| **FR-03** | Пользователь должен иметь возможность добавить товар на склад по его названию, указав количество. | Высокий |
| **FR-04** | При добавлении товара на склад система должна увеличивать текущий остаток в базе данных. | Высокий |
| **FR-05** | Если товар с указанным названием не найден в каталоге, система должна вывести сообщение об ошибке. | Средний |
| **FR-06** | Количество при приёмке должно быть положительным числом (дробные значения допускаются). | Средний |

### 2.2. Оформление продажи

| ID | Требование | Приоритет |
|----|-----------|-----------|
| **FR-07** | Пользователь должен иметь возможность добавить товар в корзину, введя его точное название и количество. | Высокий |
| **FR-08** | Система должна автоматически проверять наличие товара на складе. Если запрошенное количество превышает остаток, операция блокируется с выводом сообщения о доступном количестве. | Высокий |
| **FR-09** | При успешном добавлении товара в корзину остаток на складе должен уменьшаться мгновенно (до момента оформления чека). | Высокий |
| **FR-10** | Корзина должна отображать список добавленных товаров с указанием количества, цены за единицу и суммы по позиции. | Высокий |
| **FR-11** | Корзина должна показывать итоговую сумму всех позиций. | Высокий |
| **FR-12** | При нажатии кнопки "Купить" система должна сформировать чек (запись в таблицы `reseipts` и `sale_items`) и показать его пользователю. | Высокий |
| **FR-13** | После оформления покупки корзина должна быть очищена. | Средний |
| **FR-14** | Чек должен содержать: номер чека, дату и время, список позиций (товар, количество, цена, сумма), итоговую сумму. | Средний |

### 2.3. Обработка возвратов

| ID | Требование | Приоритет |
|----|-----------|-----------|
| **FR-15** | Пользователь должен иметь возможность найти продажу по номеру чека. | Высокий |
| **FR-16** | Система должна отображать только те товары из чека, которые ещё не были возвращены (или возвращены частично). | Высокий |
| **FR-17** | Для каждой позиции должно отображаться доступное для возврата количество (продано минус уже возвращено). | Высокий |
| **FR-18** | При оформлении возврата пользователь должен указать количество и выбрать причину из списка: "Не подошёл", "Брак", "Передумал", "Другое". | Высокий |
| **FR-19** | Количество возврата не может превышать доступное для возврата количество позиции. | Высокий |
| **FR-20** | При успешном возврате система должна автоматически восстановить остаток товара на складе. | Высокий |
| **FR-21** | Информация о возврате должна сохраняться в таблице `returns` с указанием причины и даты. | Средний |

### 2.4. Сборка ПК

| ID | Требование | Приоритет |
|----|-----------|-----------|
| **FR-22** | Система должна предоставлять конфигуратор ПК с выбором компонентов по категориям: Процессор, Материнская плата, Видеокарта, Оперативная память, Накопитель (SSD/HDD), Блок питания, Кулер, Корпус. | Высокий |
| **FR-23** | Конфигуратор должен показывать только доступные комплектующие (остаток > 0) из категории "Комплектующие для ПК" (id_category = 2). | Высокий |
| **FR-24** | Для каждой позиции должно отображаться название, цена и текущий остаток. | Средний |
| **FR-25** | Пользователь должен иметь возможность добавить услугу "Сборка ПК" (+2000 руб.) через диалоговое окно подтверждения. | Средний |
| **FR-26** | При добавлении ПК в корзину все выбранные компоненты (и услуга сборки, если выбрана) должны добавляться как отдельные позиции чека. | Высокий |
| **FR-27** | Операция сборки должна быть атомарной: если хотя бы одного компонента не хватает, вся операция отменяется (транзакция с rollback). | Высокий |
| **FR-28** | Если услуга "Сборка ПК" отсутствует в каталоге, система должна автоматически создать её при первом использовании. | Низкий |

### 2.5. Статистика продаж

| ID | Требование | Приоритет |
|----|-----------|-----------|
| **FR-29** | Пользователь должен иметь возможность ввести дату в формате ГГГГ-ММ-ДД. | Высокий |
| **FR-30** | Система должна выводить самый продаваемый товар за указанную дату с указанием количества проданных единиц. | Высокий |
| **FR-31** | Если за указанную дату продаж не было, система должна вывести соответствующее сообщение. | Средний |
| **FR-32** | Формат даты должен валидироваться: длина 10 символов, разделители "-", корректная календарная дата. | Средний |

## 3. Нефункциональные требования

### 3.1. Технические требования

| ID | Требование |
|----|-----------|
| **NFR-01** | Хранение данных должно осуществляться в реляционной СУБД SQLite с поддержкой внешних ключей (`PRAGMA foreign_keys = ON`). |
| **NFR-02** | Графический интерфейс должен быть реализован на стандартной библиотеке Python `tkinter`. |
| **NFR-03** | Приложение должно поддерживать кириллицу (UTF-8) во всех полях ввода и вывода. |
| **NFR-04** | Инициализация базы данных должна происходить автоматически из CSV-файлов при первом запуске (таблицы заполняются только если пусты). |
| **NFR-05** | Система должна работать с начальным набором данных: 5 категорий, 40 товаров, 5 сотрудников, 5 должностей. |
| **NFR-06** | Приложение должно быть совместимо с Python 3.14 и выше. |

### 3.2. Требования к качеству

| ID | Требование |
|----|-----------|
| **NFR-07** | Бизнес-логика должна быть отделена от слоя представления (GUI) для возможности повторного использования и тестирования. |
| **NFR-08** | Система должна покрывать unit-тестами ключевые компоненты (работа с БД, товары, корзина, склад, возвраты). |
| **NFR-09** | Проект должен иметь единую точку автоматизации (Makefile) для запуска, тестирования и сборки. |
| **NFR-10** | Приложение должно быть контейнеризовано (Docker) для воспроизводимого запуска. |

### 3.3. Требования к данным

| ID | Требование |
|----|-----------|
| **NFR-11** | Остаток товара на складе (`quantity_at_storage`) не может быть отрицательным (контроль на уровне бизнес-логики). |
| **NFR-12** | Сумма всех возвратов по одной позиции чека не должна превышать исходное количество проданного товара. |
| **NFR-13** | Внешние ключи должны обеспечивать целостность ссылок (нельзя удалить товар, который фигурировал в продажах). |
| **NFR-14** | Цены и количества должны храниться как числа с плавающей точкой (REAL) для поддержки дробных значений. |

## 5. Глоссарий

| Термин | Определение |
|--------|-------------|
| **Чек (Receipt)** | Документ, фиксирующий факт продажи. Содержит список позиций и итоговую сумму. |
| **Позиция чека (SaleItem)** | Конкретный товар в составе чека с указанием количества и цены. |
| **Возврат (Return)** | Операция частичного или полного возврата товара из продажи с восстановлением остатка на складе. |
| **Остаток на складе** | Текущее количество единиц товара, доступное для продажи. |
| **Сборка ПК** | Агрегатная операция добавления в корзину набора комплектующих для компьютера. |
| **SKU** | Идентификатор товара (`id_product`). |

## 6. Ограничения и допущения

1. **Однопользовательский режим**: Система не поддерживает одновременную работу нескольких кассиров (нет механизма блокировок).
2. **Локальное хранение**: База данных SQLite хранится локально в файле `store.db`.
3. **Идентификатор кассира**: В текущей версии ID кассира жёстко задан (id_cashier = 1) и не выбирается из интерфейса.
4. **Дробные количества**: Система допускает дробные значения количества (например, 1.5 кг), что может быть полезно для весовых товаров.
5. **Валюта**: Все цены указаны в рублях (RUB), символ валюты не хранится в БД.
6. **Уникальность названий**: Система предполагает, что названия товаров уникальны (поиск по названию возвращает один результат).

## 7. Критерии приёмки

Система считается готовой к эксплуатации, если:
- ✅ Все функциональные требования (FR-01 — FR-32) реализованы и протестированы.
- ✅ Все нефункциональные требования (NFR-01 — NFR-14) выполнены.
- ✅ Unit-тесты покрывают ключевые компоненты (покрытие > 70%).
- ✅ Приложение запускается командой `make run`.
- ✅ Тесты проходят командой `make test`.
- ✅ Docker-образ собирается и запускается командой `make compose-up`.
- ✅ Документация (README, specification, architecture, domain) актуальна и соответствует коду.
